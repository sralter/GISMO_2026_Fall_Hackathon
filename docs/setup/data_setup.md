# Local data setup

Run these commands from the repository root after `uv sync`. Data files stay
local and Git-ignored. This guide and the setup script are tracked independently
of the application and chatbot.

## Expected layout

```text
data/
├── buildings/
│   ├── 09_NYC_Building_Footprints.parquet
│   ├── 18_NYC_Solar_Candidates_With_Radiation.parquet
│   ├── 26_dob_solar_approved_permits_11142026.parquet
│   └── roof_solar/                         # generated locally
└── DA_WISE_GML/
    ├── DeliveryArea.shp
    ├── DeliveryArea.shx
    ├── DeliveryArea.dbf
    ├── DeliveryArea.prj
    ├── DeliveryArea.sbn                    # optional spatial index
    ├── DeliveryArea.sbx                    # optional spatial index
    ├── DeliveryArea.shp.xml                # optional metadata
    └── DA_WISE_GMLs/
        ├── DA1_3D_Buildings_Merged.gml
        ├── ...
        └── DA20_3D_Buildings_Merged.gml
```

| Feature | Inputs |
| --- | --- |
| Building shadows, roof-area queries, calculated solar resource | `09_NYC_Building_Footprints.parquet` |
| June 21 reference-exposure map and queries | Footprints plus `18_NYC_Solar_Candidates_With_Radiation.parquet` |
| Height impact | `09_NYC_Building_Footprints.parquet` |
| Permit sites in Height impact | Also `26_dob_solar_approved_permits_11142026.parquet` (optional) |
| CityGML explorer and mesh notebooks | Compatible GML file for the selected delivery area; see version limitation below |
| First inspection notebook's delivery-area map | Also the four required `DeliveryArea` shapefile files |

Thus the three locations in the original colleague request omit dataset **18**
and the delivery-area shapefile companions. The other numbered GIS intermediates
are not required by the application paths listed here. The separate root
`conversion.ipynb` experiment reads dataset 17 using an older `data/` path; it is
not a source-data generation workflow.

## Obtain the GMLs

The GMLs are published source data, rather than outputs generated by this project.
NYC's [3-D Building Model dataset](https://data.cityofnewyork.us/City-Government/3-D-Building-Model/tnru-abg2)
provides the [CityGML ZIP](https://maps.nyc.gov/download/3dmodel/DA_WISE_GML.zip).
NYC's [model metadata](https://github.com/CityOfNewYork/nyc-geo-metadata/blob/main/Metadata/Metadata_3DBuildingModel.md)
describes compilation from the 2014 aerial survey, followed by conversion from
DGN/ESRI multipatch formats to CityGML using FME. That city-side process is not a
conversion script in this repository.

**Existing reader limitation:** local delivery areas **1–6 use CityGML 2.0** and
pass the bounded-reader check. Areas **7–20 use CityGML 1.0** and are rejected by
the project's current CityGML 2.0-only reader. Having all 20 files on disk does
not make all delivery areas usable. The helper reports those version failures;
it does not transform namespaces or modify the reader. Supporting those areas
requires a separate parser compatibility change or a validated format conversion.

To reproduce our input layout directly from the published source:

```sh
uv run python scripts/setup_data.py download-gml
```

Or download the ZIP separately and run:

```sh
uv run python scripts/setup_data.py extract-gml --archive /path/to/DA_WISE_GML.zip
```

The helper accepts archive directory prefixes and installs recognized files in
the layout above. It preserves existing files, including ones that fail checks;
move an invalid file aside explicitly before retrying extraction. Interrupted
extraction can be rerun; interrupted downloads restart. The ZIP is temporary and
is removed after the download command exits. There are no uploads.

Allow about **874 MiB for the download and 13 GiB for extracted GMLs**, plus
temporary space for the archive and the largest individual extracted file.
The existing local 20 GMLs total approximately 12.8 GiB. A separately downloaded
ZIP avoids having to download it again when retrying extraction.

Project processing goes in the other direction: `citygml.iter_buildings` reads
GML records, `meshes.buildings_to_mesh` triangulates sampled surfaces, and the
[guided notebooks](../sra_notebooks/README.md) inspect and analyze those results.
These steps do not produce or rewrite the source GMLs. Their Z-unit assumption
remains provisional; acquisition does not establish physical measurement accuracy.

## Obtain the numbered Parquets

Ask the GIS team for the three named files and place them in `data/buildings/`.
Keep their schemas and coordinate systems intact. The repository contains no
complete export workflow for these specific snapshots, so downloading today's
public footprints alone does not reproduce these files exactly.
[The GIS overview](../gisREADME.md) provides background, but does not specify all
source snapshots, ArcGIS processing settings, joins, or export commands. Those
details must come from the original GIS producer before an exact rebuild can be
claimed. The setup helper neither generates nor modifies these Parquets.

Compatibility requirements checked by the helper:

- Footprints: WGS84 longitude/latitude WKB GeoParquet, with `geometry`,
  `height_roo`, `ground_ele`, `doitt_id`, `bin`, `base_bbl`, and `feature_co`.
  GeoParquet bounding-box covering metadata must point to existing fields;
  the map uses it for bounded reads. Height and ground elevation are interpreted
  as feet by the existing model.
- Candidates: WKB GeoParquet with a known CRS and `geometry`, `doitt_id`,
  `height_roo`, and `MEAN_1`. The existing snapshot uses EPSG:2263. Only the
  June 21 reference-exposure map reads it; Height impact no longer does.
- Permits: `Bin`, `House No`, `Street Name`, `Borough`, `Permit Status`,
  `Estimated Job Costs`, `Latitude`, and `Longitude`. Matching uses BIN.

`MEAN_1` is the colleague's fixed June 21 reference exposure with unspecified
units. It is separate from locally calculated annual kWh/m² and instantaneous
W/m²; do not relabel it as either quantity.

## Check inputs and prepare calculated results

```sh
uv run python scripts/setup_data.py check
```

This read-only command reports each input and readiness by feature. Exit status
is **0** for the complete documented setup, **1** if anything is missing or
incompatible. Optional inputs still count toward this complete-setup check;
individual features may report READY despite an overall status of 1. A subset
of compatible delivery-area GMLs is sufficient for exploring those particular
areas. With the current local mixed-version GML dataset, an overall status of 1
is expected even when every file is present; areas 1–6 and the Parquet-based
features can still be used.

Checks inspect Parquet schemas and CRS metadata, verify the required shapefile
companions are nonempty, and read one top-level building from each GML using the
existing bounded reader. They do not validate every geometry, all field values,
the shapefile contents, or solar calculations. Parser issues inside sampled
building records are not a certification failure or a guarantee of mesh quality.

After obtaining the footprints, regenerate solar calculations with the existing CLI:

```sh
uv run python -m gismo_2026_fall_hackathon.roof_solar --workers 4
uv run python -m gismo_2026_fall_hackathon.roof_solar --validate-only
```

The first command prepares default 2026 annual results and June 21/December 21
daily results. It can take several minutes or longer; use `--workers 1` to reduce
memory use. Checkpoints allow interrupted preparation to resume.

Outputs under `data/buildings/roof_solar/<fingerprint>/` are generated caches,
including geometry checkpoints, annual Parquet, daily NPZ files, and metadata.
They are not additional GIS-team inputs. Annual and selected-time map/chat
metrics require the corresponding prepared results. See the
[application guide](../README.md) for model assumptions and other dates.
